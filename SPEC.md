# heka — спецификация проекта

Минималистичный self-hosted гейтвей для AI-провайдеров: passthrough-прокси с
пулами API-ключей и авторотацией при исчерпании лимитов. Ничего лишнего.

**Статус:** черновик v0.1 (2026-07-10)

---

## 1. Мотивация

Существующие решения (LiteLLM, Bifrost, OmniRouter) решают задачу, но тащат за
собой bloat: трансляцию форматов, semantic caching, компрессию промптов
(lossy — ухудшает качество вывода), «скиллы», биллинг, тимы, UI. Для личного
использования нужно ровно три вещи:

1. **Единая точка входа** к разным провайдерам (OpenAI, Anthropic, Google,
   агрегаторы: OpenRouter, OpenCode Zen).
2. **Авторотация ключей**: если ключ упёрся в rate limit / quota — прозрачно
   ретраим запрос со следующим ключом из пула.
3. **OAuth-подписки как API**: подписки Claude/ChatGPT/Gemini доступны через
   API-интерфейс (делегируется в [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)
   как sidecar).

Плюс то же самое для web-search API (Tavily, Exa) — тоже пулы ключей, тоже
ротация.

## 2. Принципы

- **Passthrough, не трансляция.** heka не парсит и не переписывает тела
  запросов/ответов. Клиент говорит на нативном формате провайдера
  (`/v1/messages` для Anthropic, `/v1/chat/completions` для OpenAI и т.д.),
  heka только выбирает ключ, подставляет auth и проксирует байты как есть.
- **Один статический бинарь** (Go), один конфиг-файл, ноль внешних зависимостей
  в рантайме (кроме опционального sidecar).
- **Stateless по данным.** Никакой БД: состояние ключей (cooldown) живёт в
  памяти, конфиг — на диске. Рестарт = чистое состояние, это приемлемо. То же
  касается истории запросов для дашборда (§4.8) — ограниченный кольцевой
  буфер в памяти, не файл и не БД; рестарт стирает её так же, как стейт
  ключей.
- **Фичи не добавляются «на всякий случай».** Всё, что не в разделе 4 — в
  non-goals, пока не появится реальная потребность.

## 3. Non-goals

- Трансляция форматов между провайдерами (unified API) — это делает клиент
  или sidecar.
- Кэширование ответов, semantic cache.
- Компрессия/переписывание промптов.
- Guardrails, модерация, prompt management.
- Виртуальные ключи, тимы, квоты на пользователей, биллинг.
- Мульти-тенантный UI, графики/ретеншн метрик, полноценная аналитика —
  дашборд (§4.8) сознательно ограничен одним read-only экраном статистики/
  ошибок/прокси плюс редактором конфига, не более того.
- Балансировка по стоимости/латентности между провайдерами (клиент сам
  выбирает провайдера путём в URL).

## 4. Функциональные требования

### 4.1 Роутинг

Провайдер выбирается префиксом пути; префикс отрезается, остаток пути и все
query-параметры уходят в `base_url` провайдера как есть:

```
POST /anthropic/v1/messages        → https://api.anthropic.com/v1/messages
POST /openai/v1/chat/completions   → https://api.openai.com/v1/chat/completions
POST /google/v1beta/models/...     → https://generativelanguage.googleapis.com/v1beta/models/...
POST /openrouter/api/v1/chat/...   → https://openrouter.ai/api/v1/chat/...
POST /tavily/search                → https://api.tavily.com/search
POST /exa/search                   → https://api.exa.ai/search
POST /oauth/v1/messages            → http://127.0.0.1:<sidecar-port>/v1/messages
```

Имена префиксов задаются в конфиге, ничего не захардкожено. Провайдер — это
просто `base_url` + способ подстановки ключа + пул ключей, поэтому Tavily/Exa
не отличаются от LLM-провайдеров и новые сервисы добавляются одной секцией
конфига.

### 4.2 Входящая авторизация

- Один или несколько статических токенов гейтвея в конфиге.
- Клиент передаёт токен любым из стандартных способов (`Authorization: Bearer`,
  `x-api-key`) — heka принимает оба, вырезает его и подставляет реальный ключ
  провайдера.
- Запрос без валидного токена → `401` (кроме `/healthz`).

### 4.3 Пулы ключей и ротация

Для каждого провайдера — упорядоченный пул ключей. Состояния ключа:

- `active` — доступен для выбора;
- `cooldown(until)` — временно исключён после rate-limit ответа;
- `disabled` — исключён до рестарта/ручного сброса после ответа,
  означающего невалидность ключа.

Вместе с переходом в `cooldown`/`disabled` на ключе запоминается **последняя
ошибка** (`last_error`): причина, HTTP-код и текст ответа апстрима (первые
8 КБ; тело при этом целиком доходит до клиента — читается только «голова» и
возвращается обратно в поток). Это то, что отличает отозванный ключ от
кончившихся денег и от опечатки. Ошибка живёт до первого успеха этого ключа
или до сброса состояния.

**Выбор ключа:** round-robin среди `active`. Если все в cooldown — берётся
ключ с ближайшим `until` (запрос уходит, пусть провайдер сам ответит 429).

**Affinity (§4.3.1)** переопределяет round-robin для запросов, у которых
удалось определить кэшируемый префикс.

#### 4.3.1 Affinity: привязка диалога к ключу

Prompt cache у провайдеров живёт на конкретном ключе (организации), поэтому
чистый round-robin означает cache miss на каждом ходу диалога. Запросы,
разделяющие кэшируемый префикс, привязываются к одному ключу.

**Ключ привязки** — первое, что нашлось:

1. заголовок `X-Heka-Affinity` (имя настраивается; пустое — не использовать);
2. `prompt_cache_key` из тела (явный сигнал клиента, OpenAI);
3. хэш кэшируемого префикса: `model` + `system`/`system_instruction` +
   `tools` + **первое** сообщение (`messages`/`input`/`contents`).

Хэшируется только то, что байт-стабильно между ходами: последующие сообщения
растут на каждом ходу и в хэш не попадают. Порядок полей JSON и маркеры
`cache_control` при хэшировании игнорируются — клиенты двигают breakpoint'ы
от хода к ходу, и иначе привязка слетала бы.

Если префикс не определяется (не-JSON, нет промпта, тело больше буфера) —
обычный round-robin. Для Tavily/Exa это происходит всегда.

**Выбор ключа по привязке** — rendezvous hashing (HRW) среди ключей,
доступных в момент запроса: при выпадении ключа (cooldown/disabled/уже
пробован в этом запросе) переезжает только его доля привязок, остальные
остаются на своих ключах. Идентификатор ключа для HRW берётся из самого
секрета, поэтому перестановка ключей в конфиге привязки не сбрасывает.
Ретраи внутри запроса используют ту же привязку — замена ключу выбирается
детерминированно. Курсор round-robin привязанные запросы не двигают.

Обратная сторона: пул перестаёт быть равномерно нагруженным — один тяжёлый
диалог греет свой ключ до 429, после чего cooldown уводит привязку на
следующий. Это осознанный размен на cache hit; выключается
`rotation.affinity.enabled: false` глобально или на провайдера.

**Триггеры ротации** (конфигурируемые через `cooldown_on` / `disable_on`,
глобально и на провайдера; дефолты):

| Ответ провайдера | Действие |
|---|---|
| `429` (`cooldown_on`) | cooldown ключа + ретрай следующим ключом |
| `401`, `402`, `403` (`disable_on`) | `disabled` + ретрай следующим ключом |
| `5xx` | ретрай следующим ключом (без cooldown), макс. N раз |
| сетевые ошибки / таймаут коннекта | то же, что `5xx` |

Пустой список — осознанное «никогда» (например, `disable_on: []` для
провайдера, который отвечает 403 на запросном уровне). Обрыв запроса самим
клиентом ошибкой ключа не считается и ротацию не вызывает.

**Бюджет отключений** (`max_disables`, дефолт 1): сколько ключей один запрос
имеет право перевести в `disabled`. Статусы из `disable_on` означают «ключ
мёртв», но провайдеры отвечают теми же кодами и на ошибки уровня запроса
(неподдерживаемая модель, кривое тело) — а такая ошибка одинакова для всех
ключей, и без ограничения один запрос выжигает весь пул. Исчерпав бюджет,
heka перестаёт отключать ключи и отдаёт ответ провайдера клиенту: если один и
тот же запрос отвергают несколько разных ключей, дело в запросе, а не в
ключах. Отозванный ключ при этом отключается как раньше — бюджет тратится на
него, и ретрай уходит на следующий ключ. В истории такой запрос помечается
verdict `invalid_key_capped`. `max_disables: 0` — никогда не отключать.
На cooldown (`429`) бюджет не влияет: там обход всего пула осмыслен.

**Cooldown:** из заголовка `Retry-After`, если провайдер его прислал
(`Retry-After: 0` — минимальный cooldown 1s, а не экспонента); иначе
экспоненциально от базового значения (дефолт 60s, множитель 2, потолок 1h) по
числу подряд идущих 429 на этом ключе. Успешный ответ сбрасывает счётчик и
снимает остаточный cooldown.

**Ретраи и стриминг:** тело запроса буферизуется в памяти (лимит
конфигурируемый, дефолт 10 MiB) для возможности повтора. Ретрай возможен
только до того, как клиенту отправлены заголовки ответа; ошибка посреди
SSE-стрима не ретраится — стрим просто обрывается. На практике 429/401
приходят до начала стрима, так что это покрывает основной кейс.

Если ключи кончились (все ретраи исчерпаны) — клиенту возвращается последний
ответ провайдера как есть.

### 4.4 Sidecar: CLIProxyAPI

- heka запускает cliproxyapi как дочерний процесс при старте (команда и
  аргументы — в конфиге), слушающий на localhost-порту.
- Супервизия: если процесс упал — рестарт с экспоненциальным backoff;
  healthcheck по HTTP перед включением роута.
- Роут `/oauth/*` (имя конфигурируемое) проксируется в sidecar. Ротация ключей
  к sidecar не применяется — ротацией аккаунтов управляет сам cliproxyapi.
  Если экземпляр cliproxyapi требует собственный api-key, он задаётся парой
  `key_in`/`key` в секции sidecar (один статический ключ, без пула).
- Sidecar опционален: секция не задана — heka работает без него. Также
  поддерживается режим «внешний upstream»: вместо команды указывается просто
  URL уже запущенного экземпляра; healthcheck и 503-gate применяются в обоих
  режимах.
- Логин/обновление OAuth-аккаунтов — через собственный CLI cliproxyapi, heka
  в это не вмешивается.

### 4.5 Служебные endpoint'ы

- `GET /healthz` — без авторизации; `200`, если процесс жив (+ статус sidecar
  в теле).
- `GET /status` — с авторизацией; JSON: провайдеры, состояние каждого ключа
  (индекс в пуле, маскированный ключ, state, cooldown until, счётчики
  успехов/ошибок и токенов с момента старта — §4.7.1; плюс `last_error` (§4.3) —
  последняя причина отказа: reason, HTTP-код и текст ответа апстрима).
- `POST /status/reset` — с авторизацией; сброс cooldown/disabled состояний:
  всех, по провайдеру `?provider=`, либо одного ключа
  `?provider=&key=<индекс>`.

### 4.6 Конфигурация

Один YAML-файл, живёт на диске (в проде — на persistent volume, не в образе)
и является mutable источником правды: его можно редактировать напрямую или
через дашборд (§4.8), изменения применяются hot-reload'ом без рестарта
(§4.9). Секреты — либо через интерполяцию env-переменных `${VAR}` (удобно
для первого деплоя, когда токены приходят из окружения оркестратора), либо
прямо значением в файле (что и происходит после первого сохранения через
дашборд — редактор кладёт в файл то, что в нём ввели, без принудительного
возврата к `${VAR}`). Оба стиля поддерживаются одновременно и могут
смешиваться в одном файле. Подстановка `${VAR}` выполняется на уровне
значений YAML (не сырого текста): секрет с любыми символами остаётся
непрозрачной строкой, `${...}` в комментариях игнорируется, литеральный
`${...}` экранируется как `$${...}`. Поскольку файл может содержать ключи в
открытом виде, он требует тех же прав доступа и той же осторожности с
бэкапами, что и секреты оркестратора, которые он заменяет.

```yaml
listen: "127.0.0.1:8787"

auth:
  tokens:                            # ключи API-клиентов
    - ${HEKA_TOKEN}
  user: admin                        # логин дашборда (дефолт admin)
  password_hash: ${HEKA_PASSWORD_HASH}  # bcrypt, печатает `heka -hash`;
                                     # без него дашборд выключен

rotation:            # дефолты, можно переопределить на уровне провайдера
  cooldown_base: 60s
  cooldown_max: 1h
  max_retries: 3     # макс. переключений ключа на один запрос
  max_disables: 1    # макс. ключей, которые один запрос может отключить; 0 — не отключать
  max_body_buffer: 10MiB
  # cooldown_on: [429]        # статусы -> cooldown + ретрай
  # disable_on: [401, 402, 403]  # статусы -> disabled + ретрай
  # affinity:                 # привязка диалога к ключу, §4.3.1
  #   enabled: true           # дефолт; false -> чистый round-robin
  #   header: X-Heka-Affinity # явная привязка от клиента; "" — игнорировать

providers:
  anthropic:
    base_url: https://api.anthropic.com
    key_in: { header: x-api-key }
    keys: [ "${ANTHROPIC_KEY_1}", "${ANTHROPIC_KEY_2}" ]

  openai:
    base_url: https://api.openai.com
    key_in: { header: Authorization, prefix: "Bearer " }
    keys: [ "${OPENAI_KEY_1}" ]

  google:
    base_url: https://generativelanguage.googleapis.com
    key_in: { header: x-goog-api-key }
    keys: [ "${GEMINI_KEY_1}", "${GEMINI_KEY_2}", "${GEMINI_KEY_3}" ]

  openrouter:
    base_url: https://openrouter.ai
    key_in: { header: Authorization, prefix: "Bearer " }
    keys: [ "${OPENROUTER_KEY_1}" ]

  tavily:
    base_url: https://api.tavily.com
    key_in: { header: Authorization, prefix: "Bearer " }
    keys: [ "${TAVILY_KEY_1}", "${TAVILY_KEY_2}" ]

  exa:
    base_url: https://api.exa.ai
    key_in: { header: x-api-key }
    keys: [ "${EXA_KEY_1}" ]

sidecar:
  cliproxy:
    route: oauth
    command: [ "cli-proxy-api", "--config", "/etc/cliproxy/config.yaml" ]
    port: 8317
    # либо вместо command/port — внешний экземпляр:
    # url: http://127.0.0.1:8317
    # если cliproxyapi требует свой api-key:
    # key_in: { header: Authorization, prefix: "Bearer " }
    # key: ${CLIPROXY_KEY}
```

`key_in` покрывает три способа подстановки: header (с опциональным префиксом),
query-параметр (`{ query: key }` — на случай legacy Gemini-клиентов), и этого
достаточно для всех перечисленных провайдеров.

### 4.7 Наблюдаемость

- Структурированные логи (slog, JSON или text): по одному событию на запрос —
  провайдер, путь, маскированный ключ, статус, длительность, число ретраев.
  Тела запросов/ответов **не логируются** и никогда не пишутся на диск. Они
  могут храниться **только в памяти**, только на маршрутах, где это явно
  включено (`capture.body`, дефолт `false`, §4.6/4.8), с лимитом размера на
  запись и суммарным бюджетом на всю историю — и исчезают вместе с историей
  запросов при рестарте (§2). Это не смягчение принципа «тела не логируются»,
  а отдельная, по умолчанию выключенная возможность поверх него.
- События ротации (cooldown, disable, sidecar restart) и ошибки reload —
  отдельными строками уровня WARN/ERROR; те же строки дублируются в
  in-memory историю ошибок дашборда (§4.8), сами логи в stdout/stderr при
  этом не меняются.
- Prometheus `/metrics` — **не в MVP**, добавим при потребности (non-goal до
  тех пор).

#### 4.7.1 Учёт токенов и cache hit rate

Из успешных ответов вычитывается token usage провайдера и накапливается **на
ключ** (в `/status` и дашборде) и **на запрос** (в истории). Нормализованные
поля, одинаковые для всех провайдеров:

| Поле | Смысл |
|---|---|
| `input_tokens` | весь промпт, **включая** прочитанное из кэша |
| `cache_read_tokens` | из него — обслужено кэшем |
| `cache_write_tokens` | из него — записано в кэш (только Anthropic) |
| `output_tokens` | ответ |

`cache_hit_rate` = `cache_read_tokens / input_tokens` — метрика, по которой
видно, работает ли affinity (§4.3.1). Считается на ключ; `null`, пока
провайдер не отдал ни одного input-токена (Tavily/Exa — всегда).

Нормализация нужна из-за расхождения диалектов: у Anthropic `input_tokens`
кэш **не включает** (его добавляем обратно), у OpenAI Chat `prompt_tokens`
включает, у OpenAI Responses `input_tokens` тоже включает, у Gemini —
`usageMetadata.promptTokenCount`.

Тело ответа при этом не буферизуется: байты просматриваются по пути к
клиенту, у SSE парсятся только события с usage (у Anthropic вход приходит в
`message_start`, финальный выход — в `message_delta`, поэтому по каждому полю
берётся максимум). Ответы в неизвестной кодировке (`br`, `zstd`) и одиночные
фрагменты больше лимита пропускаются — статистика по ним просто не набегает.

### 4.8 Дашборд

Один HTTP-роут `/dashboard` (и всё под ним), встроен в бинарь heka через
`go:embed` — статический HTML/CSS/JS без сборки и без фреймворка, отдаётся
тем же процессом и портом, что и прокси. Три вкладки: обзор (агрегированная
статистика, состояние пулов ключей и sidecar'ов — переиспользует те же
данные, что `/status`, включая cache hit rate по ключам — §4.7.1), запросы
(последние N из in-memory истории, с токенами по каждому запросу и с
захваченным телом когда `capture.body` включён) и редактор конфига (§4.9).

У каждого ключа на вкладке обзора есть кнопки: `reset` — ручной сброс
состояния именно этого ключа (`POST /dashboard/api/status/reset?provider=
&key=`), чтобы вернуть в ротацию ключ, проблему которого починили на стороне
провайдера, не трогая остальные; и `why?` — раскрывает панель с последней
ошибкой ключа (HTTP-код и полный текст ответа апстрима, §4.3). Без неё
`disabled` — это состояние без объяснения: отозванный ключ, кончившиеся
деньги и опечатка выглядят одинаково.

Третья кнопка — `check` (`POST /dashboard/api/status/check?provider=&key=`):
шлёт этим одним ключом настоящий запрос на один токен (`max_tokens: 1`,
модель из `check_model` провайдера, `POST /v1/chat/completions`) и записывает
вердикт в пул так же, как это сделал бы проксированный запрос — 429 уводит
ключ в cooldown, 401 отключает, 200 очищает и то и другое. Она нужна там, где
лимит на стороне провайдера длиннее `cooldown_max`: heka остывает час и снова
считает ключ `active`, хотя апстрим держит его в бане неделю. Отличить одно от
другого может только реальный запрос. Кнопка показывается только у провайдеров
с `check_model`; результат виден там же, где и всегда — в пилюле состояния,
счётчиках и панели `why?`, отдельного вывода у кнопки нет.

Статическая оболочка (`/dashboard`, `/dashboard/*.js`, `*.css`) секретов не
содержит и отдаётся без авторизации — это и есть страница с формой входа.

Авторизация дашборда — логин и пароль, а не токен гейтвея: токен создан для
машины, которая шлёт его в каждом запросе, а человеку нужно ввести пароль
один раз. Пара `auth.user` / `auth.password_hash` (bcrypt; плейнтекст не
хранится нигде, хеш печатает `heka -hash`) обменивается через
`POST /dashboard/api/login` на сессию — случайный id в `HttpOnly`-куке с
`Path=/dashboard`, `SameSite=Lax` и `Secure` при доступе по HTTPS. Всё под
`/dashboard/api/*` требует эту куку; токен гейтвея дашборд не открывает.
Сессии живут только в памяти процесса (12 часов, рестарт разлогинивает всех)
— хранилища сессий нет, и это осознанно: инстанс один. Смена пароля в
конфиге сбрасывает все открытые сессии, обычный reload — нет.
`POST /dashboard/api/logout` завершает текущую.

Если `auth.user`/`auth.password_hash` не заданы, дашборд просто выключен
(`404` с подсказкой) — незаданный пароль не может означать открытый доступ.
Дефолтного пароля нет и хеш ниоткуда не берётся сам: задан только
`password_hash` — логин доопределяется как `admin`; задан только `user` —
это ошибка конфига (кто-то явно хотел вход и забыл пароль).

История запросов — тот же ограниченный in-memory кольцевой буфер, что
упомянут в §2 (`history.size`, дефолт 500; `history.max_bytes` — суммарный
бюджет на захваченные тела, старые тела вытесняются раньше, чем записи
целиком). `/status`, показываемый в дашборде, остаётся маскированным как и
раньше; вкладка редактора конфига — единственное место, где ключи видны в
открытом виде (см. §4.9).

### 4.9 Hot-reload

Заменяет ответ из §7: изначально «рестарта достаточно» было верно, пока
конфиг жил в образе. Как только конфиг переехал на persistent volume и стал
редактируемым через дашборд (§4.6), рестарт на каждое изменение стал бы
неприемлемым UX — поэтому reload теперь hot, применяется без падения
активных соединений.

Три источника одного и того же применения:

1. `PUT /dashboard/api/config` — редактор дашборда;
2. `SIGHUP` — для правки файла из консоли/автоматизации;
3. фоновый watcher (интервал `dashboard.watch`, дефолт 10s) — подхватывает
   правки файла напрямую на volume, без захода в контейнер.

Применение атомарно: новый набор роутов/пулов/sidecar-состояний собирается
целиком, и только затем подменяется одним указателем — ни один запрос не
видит смесь старого и нового. Пул ключей и sidecar-процесс, чья
конфигурация не изменилась, переиспользуются как есть (без сброса
cooldown/disabled состояния и счётчиков, без перезапуска процесса).
Единственное известное ограничение: если у изменившегося sidecar'а
меняется команда/порт, его маршрут отвечает `503` на несколько секунд, пока
старый процесс останавливается и стартует новый (нужно, чтобы не
столкнуться портами) — остальные маршруты это не затрагивает. Невалидный
конфиг отклоняется целиком (ошибка валидации), не меняя ни работающий
процесс, ни файл на диске. Поле `listen` применить на лету нельзя — такое
изменение сохраняется в файл, но требует ручного рестарта.

## 5. Архитектура

```
клиент ──▶ heka (один процесс Go)
            ├─ auth middleware (токен гейтвея; сессия — для дашборда)
            ├─ router (префикс пути → провайдер)
            ├─ key pool manager (состояния, round-robin, cooldown)
            ├─ reverse proxy (httputil.ReverseProxy, буферизация тела,
            │                 ретрай-цикл, стриминг ответа как есть)
            └─ sidecar supervisor (exec + backoff + healthcheck)
                     └──▶ cliproxyapi ──▶ OAuth-провайдеры
```

- stdlib-first: `net/http`, `net/http/httputil`; из зависимостей — только
  YAML-парсер.
- Состояние пула — в памяти, под мьютексом; персистентность не нужна.
- Graceful shutdown: SIGTERM → дождаться in-flight запросов (с таймаутом),
  погасить sidecar.

## 6. Этапы

- **M1 — ядро:** конфиг, auth, роутинг, passthrough-прокси со стримингом,
  пул ключей с ротацией и cooldown. Один провайдер end-to-end (Anthropic).
- **M2 — все провайдеры:** OpenAI, Google, OpenRouter, Tavily, Exa; `/status`
  и `/status/reset`; интеграционные тесты с mock-upstream (429/401/стриминг).
- **M3 — sidecar:** супервизия cliproxyapi, healthcheck, режим внешнего URL.
- **M4 — полировка:** hot-reload конфига (SIGHUP, watcher файла, дашборд —
  готово, см. §4.9), README, релизные сборки (goreleaser), systemd/launchd
  юниты.
- **M5 — дашборд и редактируемый конфиг:** in-memory история запросов/ошибок
  (§4.7), read-only UI статистики/прокси (§4.8), конфиг на persistent volume
  с редактором и hot-reload (§4.9) — готово.
