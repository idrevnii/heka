# heka — спецификация проекта

Минималистичный self-hosted гейтвей для AI-провайдеров: passthrough-прокси с
пулами API-ключей и авторотацией при исчерпании лимитов. Ничего лишнего.

**Статус:** черновик v0.1 (2026-07-10)

---

## 1. Мотивация

Существующие решения (LiteLLM, Bifrost, OmniRouter) решают задачу, но тащат за
собой bloat: трансляцию форматов, semantic caching, компрессию промптов
(lossy — ухудшает качество вывода), «скиллы», биллинг, тимы, UI. Для личного
использования нужно ровно три вещи:

1. **Единая точка входа** к разным провайдерам (OpenAI, Anthropic, Google,
   агрегаторы: OpenRouter, OpenCode Zen).
2. **Авторотация ключей**: если ключ упёрся в rate limit / quota — прозрачно
   ретраим запрос со следующим ключом из пула.
3. **OAuth-подписки как API**: подписки Claude/ChatGPT/Gemini доступны через
   API-интерфейс (делегируется в [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)
   как sidecar).

Плюс то же самое для web-search API (Tavily, Exa) — тоже пулы ключей, тоже
ротация.

## 2. Принципы

- **Passthrough, не трансляция.** heka не парсит и не переписывает тела
  запросов/ответов. Клиент говорит на нативном формате провайдера
  (`/v1/messages` для Anthropic, `/v1/chat/completions` для OpenAI и т.д.),
  heka только выбирает ключ, подставляет auth и проксирует байты как есть.
- **Один статический бинарь** (Go), один конфиг-файл, ноль внешних зависимостей
  в рантайме (кроме опционального sidecar).
- **Stateless по данным.** Никакой БД: состояние ключей (cooldown) живёт в
  памяти, конфиг — на диске. Рестарт = чистое состояние, это приемлемо.
- **Фичи не добавляются «на всякий случай».** Всё, что не в разделе 4 — в
  non-goals, пока не появится реальная потребность.

## 3. Non-goals

- Трансляция форматов между провайдерами (unified API) — это делает клиент
  или sidecar.
- Кэширование ответов, semantic cache.
- Компрессия/переписывание промптов.
- Guardrails, модерация, prompt management.
- Виртуальные ключи, тимы, квоты на пользователей, биллинг.
- Web UI / дашборд.
- Балансировка по стоимости/латентности между провайдерами (клиент сам
  выбирает провайдера путём в URL).

## 4. Функциональные требования

### 4.1 Роутинг

Провайдер выбирается префиксом пути; префикс отрезается, остаток пути и все
query-параметры уходят в `base_url` провайдера как есть:

```
POST /anthropic/v1/messages        → https://api.anthropic.com/v1/messages
POST /openai/v1/chat/completions   → https://api.openai.com/v1/chat/completions
POST /google/v1beta/models/...     → https://generativelanguage.googleapis.com/v1beta/models/...
POST /openrouter/api/v1/chat/...   → https://openrouter.ai/api/v1/chat/...
POST /tavily/search                → https://api.tavily.com/search
POST /exa/search                   → https://api.exa.ai/search
POST /oauth/v1/messages            → http://127.0.0.1:<sidecar-port>/v1/messages
```

Имена префиксов задаются в конфиге, ничего не захардкожено. Провайдер — это
просто `base_url` + способ подстановки ключа + пул ключей, поэтому Tavily/Exa
не отличаются от LLM-провайдеров и новые сервисы добавляются одной секцией
конфига.

### 4.2 Входящая авторизация

- Один или несколько статических токенов гейтвея в конфиге.
- Клиент передаёт токен любым из стандартных способов (`Authorization: Bearer`,
  `x-api-key`) — heka принимает оба, вырезает его и подставляет реальный ключ
  провайдера.
- Запрос без валидного токена → `401` (кроме `/healthz`).

### 4.3 Пулы ключей и ротация

Для каждого провайдера — упорядоченный пул ключей. Состояния ключа:

- `active` — доступен для выбора;
- `cooldown(until)` — временно исключён после rate-limit ответа;
- `disabled` — исключён до рестарта/ручного сброса после ответа,
  означающего невалидность ключа.

**Выбор ключа:** round-robin среди `active`. Если все в cooldown — берётся
ключ с ближайшим `until` (запрос уходит, пусть провайдер сам ответит 429).

**Триггеры ротации** (конфигурируемые через `cooldown_on` / `disable_on`,
глобально и на провайдера; дефолты):

| Ответ провайдера | Действие |
|---|---|
| `429` (`cooldown_on`) | cooldown ключа + ретрай следующим ключом |
| `401`, `402`, `403` (`disable_on`) | `disabled` + ретрай следующим ключом |
| `5xx` | ретрай следующим ключом (без cooldown), макс. N раз |
| сетевые ошибки / таймаут коннекта | то же, что `5xx` |

Пустой список — осознанное «никогда» (например, `disable_on: []` для
провайдера, который отвечает 403 на запросном уровне). Обрыв запроса самим
клиентом ошибкой ключа не считается и ротацию не вызывает.

**Cooldown:** из заголовка `Retry-After`, если провайдер его прислал
(`Retry-After: 0` — минимальный cooldown 1s, а не экспонента); иначе
экспоненциально от базового значения (дефолт 60s, множитель 2, потолок 1h) по
числу подряд идущих 429 на этом ключе. Успешный ответ сбрасывает счётчик и
снимает остаточный cooldown.

**Ретраи и стриминг:** тело запроса буферизуется в памяти (лимит
конфигурируемый, дефолт 10 MiB) для возможности повтора. Ретрай возможен
только до того, как клиенту отправлены заголовки ответа; ошибка посреди
SSE-стрима не ретраится — стрим просто обрывается. На практике 429/401
приходят до начала стрима, так что это покрывает основной кейс.

Если ключи кончились (все ретраи исчерпаны) — клиенту возвращается последний
ответ провайдера как есть.

### 4.4 Sidecar: CLIProxyAPI

- heka запускает cliproxyapi как дочерний процесс при старте (команда и
  аргументы — в конфиге), слушающий на localhost-порту.
- Супервизия: если процесс упал — рестарт с экспоненциальным backoff;
  healthcheck по HTTP перед включением роута.
- Роут `/oauth/*` (имя конфигурируемое) проксируется в sidecar. Ротация ключей
  к sidecar не применяется — ротацией аккаунтов управляет сам cliproxyapi.
  Если экземпляр cliproxyapi требует собственный api-key, он задаётся парой
  `key_in`/`key` в секции sidecar (один статический ключ, без пула).
- Sidecar опционален: секция не задана — heka работает без него. Также
  поддерживается режим «внешний upstream»: вместо команды указывается просто
  URL уже запущенного экземпляра; healthcheck и 503-gate применяются в обоих
  режимах.
- Логин/обновление OAuth-аккаунтов — через собственный CLI cliproxyapi, heka
  в это не вмешивается.

### 4.5 Служебные endpoint'ы

- `GET /healthz` — без авторизации; `200`, если процесс жив (+ статус sidecar
  в теле).
- `GET /status` — с авторизацией; JSON: провайдеры, состояние каждого ключа
  (маскированный ключ, state, cooldown until, счётчики успехов/ошибок с
  момента старта).
- `POST /status/reset` — с авторизацией; сброс cooldown/disabled состояний
  (всех или по провайдеру `?provider=`).

### 4.6 Конфигурация

Один YAML-файл. Секреты — через интерполяцию env-переменных `${VAR}`.
Подстановка выполняется на уровне значений YAML (не сырого текста): секрет с
любыми символами остаётся непрозрачной строкой, `${...}` в комментариях
игнорируется, литеральный `${...}` экранируется как `$${...}`.

```yaml
listen: "127.0.0.1:8787"

auth:
  tokens:
    - ${HEKA_TOKEN}

rotation:            # дефолты, можно переопределить на уровне провайдера
  cooldown_base: 60s
  cooldown_max: 1h
  max_retries: 3     # макс. переключений ключа на один запрос
  max_body_buffer: 10MiB
  # cooldown_on: [429]        # статусы -> cooldown + ретрай
  # disable_on: [401, 402, 403]  # статусы -> disabled + ретрай

providers:
  anthropic:
    base_url: https://api.anthropic.com
    key_in: { header: x-api-key }
    keys: [ "${ANTHROPIC_KEY_1}", "${ANTHROPIC_KEY_2}" ]

  openai:
    base_url: https://api.openai.com
    key_in: { header: Authorization, prefix: "Bearer " }
    keys: [ "${OPENAI_KEY_1}" ]

  google:
    base_url: https://generativelanguage.googleapis.com
    key_in: { header: x-goog-api-key }
    keys: [ "${GEMINI_KEY_1}", "${GEMINI_KEY_2}", "${GEMINI_KEY_3}" ]

  openrouter:
    base_url: https://openrouter.ai
    key_in: { header: Authorization, prefix: "Bearer " }
    keys: [ "${OPENROUTER_KEY_1}" ]

  tavily:
    base_url: https://api.tavily.com
    key_in: { header: Authorization, prefix: "Bearer " }
    keys: [ "${TAVILY_KEY_1}", "${TAVILY_KEY_2}" ]

  exa:
    base_url: https://api.exa.ai
    key_in: { header: x-api-key }
    keys: [ "${EXA_KEY_1}" ]

sidecar:
  cliproxy:
    route: oauth
    command: [ "cli-proxy-api", "--config", "/etc/cliproxy/config.yaml" ]
    port: 8317
    # либо вместо command/port — внешний экземпляр:
    # url: http://127.0.0.1:8317
    # если cliproxyapi требует свой api-key:
    # key_in: { header: Authorization, prefix: "Bearer " }
    # key: ${CLIPROXY_KEY}
```

`key_in` покрывает три способа подстановки: header (с опциональным префиксом),
query-параметр (`{ query: key }` — на случай legacy Gemini-клиентов), и этого
достаточно для всех перечисленных провайдеров.

### 4.7 Наблюдаемость

- Структурированные логи (slog, JSON или text): по одному событию на запрос —
  провайдер, путь, маскированный ключ, статус, длительность, число ретраев.
  Тела запросов/ответов **не логируются**.
- События ротации (cooldown, disable, sidecar restart) — отдельными строками
  уровня WARN.
- Prometheus `/metrics` — **не в MVP**, добавим при потребности (non-goal до
  тех пор).

## 5. Архитектура

```
клиент ──▶ heka (один процесс Go)
            ├─ auth middleware (токен гейтвея)
            ├─ router (префикс пути → провайдер)
            ├─ key pool manager (состояния, round-robin, cooldown)
            ├─ reverse proxy (httputil.ReverseProxy, буферизация тела,
            │                 ретрай-цикл, стриминг ответа как есть)
            └─ sidecar supervisor (exec + backoff + healthcheck)
                     └──▶ cliproxyapi ──▶ OAuth-провайдеры
```

- stdlib-first: `net/http`, `net/http/httputil`; из зависимостей — только
  YAML-парсер.
- Состояние пула — в памяти, под мьютексом; персистентность не нужна.
- Graceful shutdown: SIGTERM → дождаться in-flight запросов (с таймаутом),
  погасить sidecar.

## 6. Этапы

- **M1 — ядро:** конфиг, auth, роутинг, passthrough-прокси со стримингом,
  пул ключей с ротацией и cooldown. Один провайдер end-to-end (Anthropic).
- **M2 — все провайдеры:** OpenAI, Google, OpenRouter, Tavily, Exa; `/status`
  и `/status/reset`; интеграционные тесты с mock-upstream (429/401/стриминг).
- **M3 — sidecar:** супервизия cliproxyapi, healthcheck, режим внешнего URL.
- **M4 — полировка:** hot-reload конфига по SIGHUP, README, релизные сборки
  (goreleaser), systemd/launchd юниты.
